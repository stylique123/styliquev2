# ⚠️ DESTRUCTIVE MIGRATION — BACKUP REQUIRED

This migration drops `Creative` and `CreativeSet` tables with `CASCADE`. Any rows
in those tables (and any rows in tables with FKs into them) are **lost** when this
runs against the live DB.

## Before running `prisma migrate deploy`

```bash
# 1. Snapshot the live DB (Neon → branch / restore point, or pg_dump for self-hosted)
neon branches create --name pre-remove-creative-studio-$(date +%Y%m%d)
# OR:
pg_dump "$DATABASE_URL" --clean --if-exists > pre-remove-creative-studio-$(date +%Y%m%d).sql

# 2. (Optional) Export the rows you're losing so they're recoverable as CSV
psql "$DATABASE_URL" -c "\copy (SELECT * FROM \"Creative\") TO 'creative-backup.csv' CSV HEADER"
psql "$DATABASE_URL" -c "\copy (SELECT * FROM \"CreativeSet\") TO 'creativeset-backup.csv' CSV HEADER"

# 3. Run the migration
pnpm --filter @stylique/db prisma migrate deploy

# 4. Verify the drops worked + nothing else broke
psql "$DATABASE_URL" -c "\d Creative" # should error: relation does not exist
psql "$DATABASE_URL" -c "SELECT count(*) FROM \"AnalyticsEvent\";" # smoke check unrelated tables
```

## Rollback if anything's wrong

```bash
# Restore from Neon branch
neon branches restore <branch-name>
# OR from pg_dump
psql "$DATABASE_URL" < pre-remove-creative-studio-<date>.sql
```

## What gets dropped

- `Creative` table (every creative generated by Studio)
- `CreativeSet` table (every creative-set queue row)
- Enum types: `CreativeRole`, `QcState`, `CreativeSetStatus`

## What is NOT dropped

The Plan quota columns (`monthlyCreatives`, `monthlyCreativeSets`, `creativeSets`)
and dormant `CREATIVE_*` values in `EventName` / `UsageMetric` enums are
intentionally left in place. A future cleanup migration can remove them once
all dashboard code paths are confirmed to no longer reference them.
